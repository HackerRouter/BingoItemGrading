# 顺序约束与预算定价

章节号与 [`route-competition-scoring.md`](route-competition-scoring.md) 连续。

## 十二、顺序：材料来源不能比现状更靠后

前面几节都在讲价格，但价格会骗人。真实的坑是**依赖顺序**：

```
下界入口 ← 黑曜石 ×10 + 点燃物
点燃物   ← 打火石 或 火焰弹
火焰弹   ← 火药 + 烈焰粉 + 煤
烈焰粉   ← 烈焰棒 ← 杀烈焰人 ← 要去下界   ← 回到起点
```

火焰弹在「点燃物」的候选里，但它自己要用下界的东西做。只看价格，
模型会挑它去点第一座门。所以还需要一条与价格无关的约束。

### 分层

```
tier(动作) = 0                              没有前置
tier(动作) = 1 + max(tier(前置物品))        有前置
tier(物品) = min(tier(产出它的动作))
```

取**最小可导出值**：从「无前置的动作」出发反复松弛，只下调。于是每个有限层号
都有一条有限长度的推导链，链底是无前置的动作；纯循环永远拿不到层号。

### 按预算定价

```
C[item][ℓ] = 前置链最多 ℓ 层时，拿到 item 的最小成本
             每个动作的前置按 C[·][ℓ-1] 定价
```

预算每往下一步减一。所以「开下界门」这件事能看到的来源，比门本身浅一层；
再往下的材料又浅一层。链条有穷，递归必然终止。

**试过但不够用的做法**：给物品定一个层号（`tier(物品) = min(产出它的动作)`），
让每个动作只在自己那一层定价。它能挡住循环，但过于僵硬——一旦某物品有了一条
浅来源（黑曜石能从废弃传送门箱子里捡，层 0），所有更深的来源（岩浆浇铸，层 2）
就永远进不了任何浅层动作的前置，哪怕那条路本身完全可行。**预算只限制链条长度，
不限制「必须用最浅的那条」。**

于是同一个物品在不同预算下价格不同，而 `C[target]` 取全部候选的合并：
「去下界挖金矿」与「主世界挖金矿」照样能比价。

### 实测（`bg plan`）

下界入口（补齐门框 + 点燃物 + 点亮）：**17.93 TU**，其中
黑曜石 4 块占 12.65（跑废弃传送门开箱）、点燃物 4.74、本地动作 0.54。

黑曜石的三条来源在同一条曲线上：

| 来源 | 单价 | 说明 |
|---|---|---|
| 废弃传送门箱子 | **3.16** | 每箱 0.9045 块，跑 172 格 |
| 岩浆浇铸 | **4.03** | 铁桶 + 下挖到浅层岩浆湖 + 每块 1 桶 |
| 鱼骨矿道挖矿 | 15244 | 贵在钻石镐，被剪枝 |

依赖深度摊开来看正是那条链：

| 深度 | 动作 |
|---|---|
| 0 | 挖铁矿、挖砂砾、挖煤、杀苦力怕、跑废弃传送门、下挖到岩浆层 |
| 1 | 铁制工具、铁桶、装岩浆、打火石、两种点火物 |
| 2 | 挖钻石矿、**下界入口** |
| 3 | 钻石镐、杀烈焰人、**岩浆浇铸** |
| 4 | 烈焰棒磨粉 |
| 5 | **合成火焰弹** |

`craft:fire_charge` 在深度 5，`portal:nether` 在深度 2；点门时前置用的是
更浅那几层的曲线，上面只有「从箱子里捡到的火焰弹」。把打火石和箱子里的
火焰弹都摘掉，下界入口就变成纯循环、不可行，并报出证据链。

### 门框要按形状数，不能按常数

一个能点着的下界门只要 **10 块**黑曜石：内部 2×3 空腔，加上**上下各 2 块横梁、
左右各 3 块立柱**。**四角不需要**——这就是最小门是 10 块、而不是 4×5 外圈那
14 块的原因：

```
. # # .     上横梁 2
# . . #     左右立柱各 3
# . . #
# . . #
. # # .     下横梁 2
```

废弃传送门的黑曜石是散乱的：`portal_10` 只剩 5 块、`portal_1` 剩 11 块、
`giant_portal_1` 有 31 块却散在不同平面上。所以「补几块」必须读模板的
**方块坐标**，在每种模板里找「最像门框的那个窗口」，数必需位上有几块。

数据在 `data/upstream/<pack>/datapack/data/minecraft/structure/ruined_portal/*.snbt`
（`bg data sync` 从上游解包结果复制），13 个模板：

| 模板 | 已有 | 缺 |
|---|---|---|
| `portal_10` | 3 | **7** |
| `giant_portal_1..3` / `portal_5` / `portal_8` | 5 | 5 |
| `portal_2` / `portal_3` / `portal_6` | 6 | 4 |
| `portal_4` | 7 | 3 |
| `portal_1` / `portal_9` | 8 | 2 |
| `portal_7` | 9 | **1** |

等权平均缺 **4.0 块**。原版没有导出「每个模板被选中的概率」（那是代码逻辑，
不在数据包里），所以按等权处理，报告里写明这一点。

两条硬规则：

- **内腔必须能站人**（6 格里至少 4 格是空气）。填满黑曜石的窗口不是门，是黑曜石堆；
- **哭泣黑曜石不算门框材料**。它能出现在必需位上，但只算缺口——这正是不能写成
  「数一数有多少块黑曜石」的原因；
- **四角不参与判定**。它有没有方块不影响能不能点火，所以既不算已有也不算缺口。

### 岩浆：主备两条其实是「按纵段拆」

岩浆的 `by_section` 每一段都是一条独立来源，成本与密度成反比：

| 纵段 | 每区块 | 挖竖井 | 走到第一片 | 成本 TU | 一片够几批 |
|---|---|---|---|---|---|
| y48~63 | 0.13 | 7 格 | 157 格 | **3.94** | 5 |
| y16~31 | 0.36 | 39 格 | 95 格 | 6.35 | 5 |
| y−32~−17 | 10.54 | 87 格 | 17 格 | 12.78 | 5 |
| y−64~−49 | 29.30 | 119 格 | 10 格 | 17.21 | 5 |

浅段挖几格就下去，但岩浆稀、要走很远；深段要挖很久，但出门就是岩浆海。
两段都进同一条曲线，先用便宜的，用满容量再换——「主备竞争」不需要特殊规则。

水平距离按**片密度**估：一片 50 块、每区块 `per_chunk` 块，
则每区块 `per_chunk / 50` 片，最近邻期望 `0.5 / sqrt(片密度) × 16` 格。

每一段用**独立的** `capability:lava_access@<y>`，不能共用一个能力项——
否则「走到浅层岩浆」这条便宜前置会去顶替深层的，成本对不上。

### 岩浆为什么不能按矿脉算

`mining.py` 的公式是「挖穿 `k / 体积密度` 个方块才碰上 k 块」，它对散点矿成立，
对**连片**资源不成立：WGSC 统计岩浆时只数连续块，到达一片就有几十块，远多于
一次动作要的量。所以成本只该算「到那儿」：

```
竖井 = (地表高度 − 该纵段上界) × 截面 × 该处围岩秒数
水平 = 0.5 / sqrt(每区块片数) × 16      ← 撞上第一片就够，不用累加 10 格
每区块片数 = per_chunk / 一片块数
```

这个估法假设段内岩浆片独立同分布，所以是**上界**：实际片更集中时第一片更近，
真值更小。

（早先用过「`1 / (截面 × 体积占比)`」，那等于假设岩浆均匀散布在段内，
会把浅段算到几千格之外，与「连成片」的事实矛盾。按片密度算才对齐。）

### 世界交互规则直接写在代码里

浇铸不是配方，也不是战利品表，是**方块更新规则**——数据包与上游产物都不会给出。
但它和拍脑袋的数字不同：它是确定性机制，写错了能对着 wiki 查出来。早先试过把它做成
`data/knowledge/transforms.toml` + `plan/transforms.py` 的表驱动声明（结构在表里、数值引用
`bingo_grading.units` 的名字），但生产路径从未接入、只有测试在用，已连同测试一起删除。
现在浇铸直接是 `sources/constructs.py` 的 `CASTING`：输入、批量、`source="game_rule"` 都在
`Construct` 上，改规则就是改一处。

三类来源就此分开记：`loot_expectation:…` 是数据导出的，`game_rule` 是机制声明的，
`calibration` 是拍的数字（只能进 `assumptions`）。

**浇筑下界门不需要钻石镐**——浇出来的黑曜石直接就是门框，站上去就完事。
钻石镐只属于「挖天然黑曜石」那条路，而那条路贵在镐：`mine:diamond` 一项就
1364.9 TU（3 颗钻石），把整条挖矿路线推到 15244 TU/块。

### 已知局限

1. **多产出按件分摊**。`craft:fire_charge` 一次出 3 个，曲线按「1/3 份投入」
   给单件定价。真的只做 1 个时，得付整整一批的钱。这是凸松弛，方向偏低。
2. **嵌套入口会被重复计价**。若某条材料的来源本身又要进一次下界，
   曲线会把它算进单价里，不做跨层合并。语义正确（确实得进去），
   但当它真的更便宜时才会被选中，而那时它本来就该被选中。
3. **开箱路线按容量无限处理**。凑 4 块黑曜石要翻 4.4 个废弃传送门箱子；
   单区域能不能凑够取决于结构密度。把这条容量改成有限值，浇铸就会进入竞争
   ——那会改动现有数值，需要单独确认。
4. **模板权重按等权**。原版选哪个废弃传送门模板是代码逻辑，数据包里没有。

### 这一节的判据

1. 晚出现的便宜来源不会被早出现的动作白拿（合成用例：早的火花 10 TU、
   晚的 13 TU，门只用前者）。
2. `craft:fire_charge` 的预算档晚于 `portal:nether`；点门那条曲线上没有它。
3. 摘掉全部早期点火物后，下界入口不可行且报出环。
4. 挖黑曜石被开箱支配（更贵 + 前置更多），剪枝后不进曲线。
5. 浇铸不进钻石镐的依赖：把开箱渠道拆掉后，方案改用 `cast:obsidian`，
   证明它没被分层挡住。
6. 岩浆的到达成本按片密度算，且标明是上界；浅段比深段便宜、深段更密。
7. 满框 10 块黑曜石时缺口为 0；去掉四角仍是完整门；外圈全换成哭泣黑曜石时缺口仍是 10。
8. 内腔填满黑曜石的窗口不当作门（返回 `None`，不是「缺 0 块」）。
9. 13 个原版模板全部能匹配出窗口，平均缺口严格小于满框。
10. 并行来源按速率相加（10/20 分钟 → 6.67），互斥仍取最小（→ 10）；
    并行组前置不一致时报错，零成本成员被拒。
11. `race` 动作不被剪枝：不标 race 时贵的被支配，标了 race 两条都在。
12. 金锭地表的村庄/废弃门两源用 `race` 合成回 **2.179 TU**（旧调和并联值），
    而不是取 min 的 3.069（那会把 score 从 1 抬到 2）。
