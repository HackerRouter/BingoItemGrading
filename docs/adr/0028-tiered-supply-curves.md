# ADR 0028：供给曲线按依赖层计价，前置是带模式的物品

> **后续修订**：`bingo_grading.graph` 已删除，并联与分组规则由 `plan/supply.py` 与 `plan/tiers.py` 继承；`transforms.toml` 与 `plan/transforms.py` 也已删除，方块变换读 `graph.json` 的 `transmutes` 边。

## 背景

`bingo_grading.graph` 的并联公式是 `1 / Σ(1 / w_i)`。它假设「几条路同时走」，
于是把一条很便宜的路稀释成「也不便宜」，与「平行路线互相竞争」正好相反。
另外它按**域**（地表/地下/下界）分组、跨域取 min，把「去下界」当成一个开关：
真实情况是「黑曜石 ×10 + 点燃物」，而这两样本身就是有价格的物品。

设计讨论见 `docs/design-route-competition.md`。落地时撞上一个方案里没写清楚的问题：

```
下界入口 ← 黑曜石 ×10 + 点燃物
点燃物   ← 打火石 或 火焰弹
火焰弹   ← 火药 + 烈焰粉 + 煤
烈焰粉   ← 烈焰棒 ← 杀烈焰人 ← 要去下界  ← 回到起点
```

只看价格的话，火焰弹可能被选来点**第一座**门——而它自己要用下界的东西做。
这不是数值算错，是**依赖顺序**错。用户的要求是：
「材料来源不能比当前现状更靠后」。

## 决定

### 1. 动作

来源表示成四元组 `(cost, yields 向量, capacity, requires)`：

- `cost` 是做一次的固定成本（TU）；
- `yields` 是做一次的产出向量——挖一块矿同时出石头、开一个箱子同时出五六种物品，
  这些产出不该各付一次旅行成本；
- `capacity` 是**次数**上限；
- `requires` 是 `[(物品, 用量, 模式)]`，模式为 `once`（工具、站点、打火石）
  或 `per_use`（黑曜石、火焰弹、燃料）。不模拟耐久，所以工具永远是 `once`。

### 2. 供给曲线

`f(n) = 取得 n 件的最小成本`，凸的分段线性：每段来自一个动作，段内单价恒定，
按单价升序拼接，段边界就是交叉点。便宜的先上场，用满容量才轮到贵的。

三条聚合规则：OR → 合并曲线；AND → `f_child(n) = f_parent(n/ratio) + fixed·(n/ratio)`；
联合产出 → 次数取 `max(n_i / y_i)`。剪枝按「更便宜 + 容量不小 + 前置不多 + 副产物不少」
判支配。

### 3. 依赖顺序：预算（本次新增的关键一条）

```
C[item][ℓ] = 前置链最多 ℓ 层时，拿到 item 的最小成本
             每个动作的前置按 C[·][ℓ-1] 定价
```

预算每往下一步减一，链条有穷，递归必然终止。于是：

- 「点门用的火焰弹要靠进过下界」这种自指要成立，得像俄罗斯套娃一样多套一层
  下界入口，因而必然更贵——它不被禁止，但永远不会赢；
- 同一条链每下一层都更严格，等于「材料来源不能比当前现状更靠后」。

**先试过、但不够用的做法**：给物品定一个层号
（`tier(动作) = 1 + max(tier(前置物品))`，`tier(物品) = min(产出它的动作)`），
让每个动作只在自己那一层定价。它能挡住循环，但过于僵硬：一旦某物品有了一条
浅来源（黑曜石能从废弃传送门箱子里捡），所有更深的来源（岩浆浇铸）就永远
进不了任何浅层动作的前置，哪怕那条路本身完全可行。预算只限制链条长度，
不限制「必须用最浅的那条」。层号仍保留，但只用于报告与循环诊断。

### 4. 世界交互规则单独一类

熔炼、浇铸、酿造、摆门点亮是**方块更新规则**，不是配方。数据包与上游产物都
不会给出，只能人工声明；但它们是确定性机制，写错了能对着 wiki 查出来。
所以单独归一类，放 `data/knowledge/transforms.toml` 声明**结构**，数值引用
`bingo_grading.units` 的名字：

```toml
[[rule]]
id = "cast:obsidian"
inputs = [{ item = "minecraft:lava", qty = 1, mode = "per_use" }]
requires = [{ item = "capability:bucket", qty = 1, mode = "once" }]
outputs = { "minecraft:obsidian" = 1 }
extra_seconds = "CAST_SECONDS_PER_BLOCK"
batch = 10
source = "game_rule"
```

三类来源就此分开记：`loot_expectation:…`（数据导出）、`game_rule`（机制声明）、
`calibration`（拍的数字，只能进 `assumptions`）。

关键一点：**浇筑下界门不需要钻石镐**——浇出来的黑曜石直接就是门框。
钻石镐只属于「挖天然黑曜石」那条路。

### 5. 形状要读模板坐标，成片资源要按纵段拆

有两类数字 `facts/` 导不出来，必须另找数据：

**门框缺几块**。一个能点着的下界门只要 **10 块**黑曜石（内部 2×3，加上下各 2
横梁、左右各 3 立柱；**四角不需要**），而废弃传送门的黑曜石是散的（`portal_10`
只剩 3 块，`portal_1` 剩 8 块）。`facts/template.jsonl`
只有「每个模板多少块某方块」的计数，没坐标，所以要把原版 SNBT 模板也同步进
`data/`（`bg data sync` 的 `structure-templates` 一类），再在每种模板里找
「最像门框的窗口」（上下各 2 + 左右各 3，四角不算）。两条硬规则：内腔必须能站人（否则是黑曜石堆，不是门）；
**哭泣黑曜石不算门框材料**，它占着必需位也只是缺口。13 个模板等权平均缺 4.0 块。

**岩浆的到达成本**。WGSC 只统计连续岩浆块，所以「要多少块」不存在——到达一片
就够。按 `by_section` 每段拆成一条独立来源：竖井深度 + 按**片密度**估的水平
距离（`0.5 / sqrt(每区块片数) × 16`）。浅段挖几格就下去但岩浆稀，深段要挖
很久但出门就是岩浆海；两段进同一条曲线，先用便宜的——「主备竞争」不需要
特殊规则。每段要有**独立的** `capability:lava_access@<y>`，共用会把浅段的便宜
前置顶替到深段头上。

> **2026-11-16 更新**：这段的散点口径已被 `lake_source` 取代。WGSC 另有
> `lava-lakes.json`，量的是**地表岩浆湖**的间距（最近 215 格）与大小（每湖 62 块），
> 一直没被读过。散点口径会算出「沿地下矿道走 145 格碰上一片 50 块的连片岩浆」
> ——既假设了连片、又走了地下 2 倍系数。现在 `patch_sources` 优先返回湖口径
> （一条来源、无竖井项），只有缺湖数据时才退回上面的纵段散点。
> 下游观测值：`minecraft:lava` 8.16 → 5.58 TU，下界入口均摊 15.55 → 12.96。
>
> 同一批改动还加了 `Requirement.forbid`（来源黑名单）：`portal:patch_ruined`
> 只是把**现成的黑曜石**塞进已有框架的缺口，不接受浇铸——挖坑浇一整框是
> 标准操作，但在别人的框架缺口上精确浇一块不是。所以「补门」与「从零垒门」
> 不仅黑曜石数量不同，**可用的来源集合**也不同。
>
> 另有 `Requirement.forbid_needs`（自举约束）：开门用的东西不能来自己经开好的门。
> 判据是「不用目标物品时拿不到的物品集」的不动点，而不是静态依赖图——
> 静态图会把「铁锭也能从下界猪灵换」错当成「铁锭必须下界」，从而把铁桶、
> 甚至黑曜石全部来源误禁（实测：按 SCC 成员判会直接让 `nether_access` 变成 `inf`）。

### 6. `domain` 降级

维度的差异已经由「哪些物品在该处有来源」表达，入口代价又进了物品曲线。
所以 `domain` 从计算维度降为**报告标签**，跨域取 min 退化成普通 OR。

## 后果

- 新增 `bingo_grading/plan/`（`actions` / `supply` / `tiers` / `requires` / `routes` / `solve` /
  `transforms`），纯计算、不做 IO；动作从哪儿来由案例层与规则表决定。
- 新增 `data/knowledge/transforms.toml`：世界交互规则。加一条新规则 = 加一段 TOML，不动代码。
- 新增 `bingo_grading.case.portal`：把「去下界」拆成一张物品子图（工具链、黑曜石三源
  ——开箱 / 浇铸 / 挖矿、燧石、火药、烈焰粉、两种点火物），数据来自统计快照
  与战利品表，标定值集中在一处并写进 `assumptions`。
- `CaseContext.patch_access_cost()`：成片资源（岩浆这类）的到达成本。
  与 `mining()` 的区别是**不需要「要多少块」**——到达一片就够。
- `bg plan` 命令输出主路线、备选段、交叉点、依赖深度、`unlocks`（每个动作
  第一次能定价的预算）与被剪掉的来源。
- `bingo_grading.graph` 的调和并联**保留不动**：它是 P3 的验收用例，且与本次改动
  没有共享代码。两套聚合的取舍见 `docs/design-route-competition.md`。

## 判据

`tests/test_plan_engine.py`、`test_plan_transforms.py`、`test_plan_portal.py`：

1. 单物品无耦合时，曲线解 = 按单价排序的贪心解。
2. 便宜来源容量为 1 时，第 2 件切段。
3. 被支配的假来源不影响解；互支配的两条来源只留一条。
4. 一个动作对每一样产出都贡献曲线（开箱同时供给黑曜石与燧石）。
5. 循环依赖不可达，并报出环的证据链。
6. 晚出现的便宜来源不会被早出现的动作白拿（火花 10 vs 13 TU）。
7. 同一个 `once` 前置在一个方案里只计一次；`per_use` 随次数线性。
8. 下界入口：`craft:fire_charge` 的预算档晚于 `portal:nether`，
   点门那条曲线上只有「从箱子里捡到的火焰弹」；把打火石与箱子里的火焰弹
   都摘掉后，下界入口变成纯循环、不可行。
9. 浇铸不依赖钻石镐；拆掉开箱渠道后方案改用 `cast:obsidian`，
   证明它没被分层挡住。
10. 规则表引用写错（常量名、方块名、模式）当场报错，不静默跟 0。
