# 来源的地理属性来自方块放置事实，不来自战利品表路径

## 背景

来源判定原先只看两样东西：`family`（上游规则族）与战利品表路径。表路径在 `blocks/` 下就判为「方块掉落」，再按方块名是否属于地下集合决定路线。

这个推断有个前提：**方块名与它所在的位置相关**。矿石是这样（`redstone_ore` 只在地下），但装饰方块不是。红石线的表在 `blocks/redstone_wire`，按名字判成地表方块，可它只由古代城市模板放置，在 y≈-51。

两件事被混成了一件：

- 战利品表说的是**破坏这个方块掉什么**。
- 方块在世界里**在哪出现**是另一个事实。

## 决策

方块的地理属性一律从**放置事实**读取，不从表路径推断。

放置事实只有两个来源，都在上游 `block:` 节点的入边里：

| 族 | 含义 | 凭据 |
|---|---|---|
| `worldgen` 且 `slot=block` | 世界生成特性放置 | `meta.source` |
| `bindings/template_block` | 结构模板放置 | `meta.templates` |

其余入边一律**不认**：

- `bridge/place` / `code/place_source`（`item:X` → `block:X`）是玩家放置，依赖已有物品。认了会成环：有红石就能放红石线，于是红石线是红石的来源。
- `code/transform` 是方块原地转换，前提是方块已存在。
- `bridge/convention` 是玩家行为结果（混凝土遇水固化）。

判定规则：**若某方块只有模板来源、没有任何世界生成特性**，则它的获取路线按模板所属的结构集合决定。模板路径 → 结构集合的映射在 `data/knowledge/structure_sets.toml` 的 `template_prefixes`。

## 后果

修复前后（`26.3` 数据）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `underground` 来源 | 302 | 426 |
| `surface` 来源 | 2591 | 2467 |
| 被识别为「只由结构放置」 | 0 | 323 |

323 条来源中 124 条从 `surface` 改判为 `underground`（古代城市、试炼密室、废弃矿井的方块）。其余 199 条仍是 `surface`——村庄、掠夺者前哨、林地府邸在地表，拆它们的门确实在地表。

新增的 `sources/placement.py` 是这条路线的唯一判定入口，`routes.decide` 只接收结论（`structure_only` + `block_sets`），不自己查图。

## 已知未尽之处

**剩余 199 条「地表结构方块」仍是 `surface`**，但它与「野外捡一个」不是同一件事：前者要找到村庄。当前 `ROUTES` 只有四种，缺一个「结构内获取」。等 P5 策略注册时再看是否需要第五种路线，现在不提前加——加了就得同时定义它的代价模型，而结构代价已经由 `structure_density` 给出，可能不需要单独路线。

**末地与下界的结构方块**（`end_city/`、`bastion/`）走不到 `other_dimension` 分支，因为现有判定只看 `subject` 与 `prereq` 里的世界节点，而模板不携带维度。数量很少（`end_city` 31 处模板），且这类方块的物品多数另有配方来源，暂不处理，但记在这里以免误以为已覆盖。

## 替代方案

**在地下集合里逐个补方块名**：治标。每改一次地形包就要重新对一遍，而且判不出「同一个方块既在地表结构也在野外生成」的情况。

**让上游直接给出方块的地理标签**：需要上游引入「位置」概念，而它的语义是存在性、刻意不判位置。这条边界该由下游承担。
