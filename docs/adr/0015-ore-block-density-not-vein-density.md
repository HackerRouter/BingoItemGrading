# 挖掘代价用矿物方块密度，不用矿簇密度

## 背景

矿石在世界里是聚簇生成的：一次 `ore_redstone` 放置会生成一簇 4–8 个红石矿。直觉上，「矿簇密度」似乎比「方块密度」更贴近玩家体验——挖矿道撞到一簇就拿到一把。

采集侧目前只提供方块级计数（`count`、`avgPerChunk`），没有任何矿簇信息（已核实：`biome-ore`、`biome-ore-nether`、`ore-exposure`、`section-block-histogram` 全文无 `cluster` / `vein` / `blob` 字段）。要不要为它新增分析器，取决于管道实际需要哪个。

## 决策

**挖掘代价用矿物方块密度。不采集矿簇。**

## 理由：期望是线性的

玩家挖矿道的成本与挖掘长度成正比。设矿道截面 `S`、长度 `L`，扫过体积 `V = S·L`。体积密度 `ρ`（方块/方块³）。

期望获得的矿石方块数：

```
E[获取] = ρ · V
```

这个式子与矿石是否聚簇**无关**。聚簇时：

```
E[获取] = E[撞到的簇数] × 每簇方块数
        = (ρ/k) · V_swath · k        （ρ/k = 簇的体密度，k = 每簇方块数）
        = ρ · V_swath                 ✓
```

簇的「碰撞截面」更大但簇数更少，两者恰好抵消。所以：

- 若目标物只缺数量上的期望，方块密度足够。
- 矿簇只影响**方差**（要么撞到整簇、要么一个都没有），不影响期望。

Bingo 的一个格子通常只要 1 个物品，而单块矿石的掉落率已在掉落表里（红石矿单块掉 4–5 个）。所以「一簇给太多」不构成实际限制。

## 「簇间距比块间距长」是对的，但它不影响挖矿代价

这句话本身正确：三维空间里最近邻距离与密度成 `ρ^(-1/3)` 关系，簇密度是块密度的 `1/k`，所以簇间距 ≈ 块间距 × `k^(1/3)`。对红石（`k=8`）是 2 倍。

但它描述的是**空间尺度**，不是**挖掘代价**。差别在于获取模式：

| 模式 | 代价由什么决定 | 聚簇的影响 |
|---|---|---|
| 鱼骨矿道 | 挖掉的方块数；路径上的矿全部入包 | 无影响 |
| 洞穴探索 | 洞穴壁覆盖率 × 壁上矿石占比 | 二阶，且方向是降低 |

挖矿道没有「走到下一处」这一步——路径本身被挖掉了。所以聚簇决定的是「这 2L 个方块里的矿集中在 3 处还是分散在 20 处」，而总数不变，总数才是代价。

探索模式下真正决定「多久看到一个矿」的是**地下空洞率**（洞壁占比），不是簇间距。那是 C11 的事。

## 用现有数据能直接算出的量

矿道截面 `S`、体积密度 `ρ`，走过 `L` 格的期望收获是 `ρ·S·L`。撞到 1 块需：

```
格/块 = 1 / (ρ_vol · S)
```

以 `26.3` 主世界实测（截面 1×2、纵段数据）：

| 矿石 | 纵段 | 体积密度（/千方块） | 约多少格撞 1 块 | 约多少格撞 1 簇（k） |
|---|---|---|---|---|
| `deepslate_redstone_ore` | y[-64,-49] | 3.69 | **135** | 1084（k=8） |
| `deepslate_diamond_ore` | y[-64,-49] | 1.77 | 283 | 1131（k=4） |
| `iron_ore` | y[16,31] | 4.70 | 106 | 957（k=9） |
| `redstone_ore` | y[0,15] | 0.59 | 842 | 6735（k=8） |

注意「撞 1 簇」恰好等于「撞 1 块 × k」——这再次说明聚簇没有让它变快或变慢。

这些数直接支撑「到达该层需要挖多少格」，不需要矿簇。

## 矿簇什么时候才值得采集

| 场景 | 是否需要用矿簇 |
|---|---|
| 目标只要 1 个物品 | 不需要，掉落表已覆盖 |
| 目标需要 N 个（如 9 个铁锭做铁块） | 边际收益递减，一簇给多个会加速完成。属二阶效应 |
| 要算「挖矿结果的不确定性」 | 需要。但当前方差由 `variance_penalty` + `reliable` + 置信区间处理，量纲不同 |
| 要模拟玩家「看到就挖」的行为 | 不需要。这在期望上与盲挖等价 |

采集矿簇的成本很高：需要对全区块做 3D 连通分量标记（19044 区块 × 384 高度），而收益是二阶的。**不做。**

## 真正缺的是纵段，不是矿簇

上面那张表能算出来，靠的是 `ore-exposure` 的 `sections`（维度级纵段）。而群系级缺这个：

- `biome-ore-nether` **已有** `sectionProfiles`（按矿石分组的纵段剖面）
- `biome-ore`（主世界）**没有**

这导致恶地金矿算不准：整柱平均 26.56/区块 换算成体积密度是 0.27/千方块（挖 16 格期望 0.009 块），但它实际集中在 `ore_gold_extra` 的 y=32~256，该段密度远高于整柱平均。

**所以 C10（群系级纵段分解）的优先级高于任何矿簇相关的工作。** 主世界版对齐下界版即可。

## 后果

- 采集侧不需要新增任何矿簇分析器，省掉一次 3D 连通分量扫描。
- P3 的挖掘代价用「体积密度 × 扫过体积」，输入是 `ore_density` + 纵段分解。
- 若日后真的需要「N 个物品」的累计代价，先检查是否已被掉落表数量覆盖；仍有缺口再议矿簇，不要提前采集。
