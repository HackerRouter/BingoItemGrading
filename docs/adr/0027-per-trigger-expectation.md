# ADR 0027：来源概率统一为「每次触发的期望件数」

## 背景

来源索引以前给每行一个 `probability`，数值来自手工表 `data/knowledge/probabilities.toml`。
那张表只有 7 条，且是抄来的：

| 条目 | 手工值 | 战利品表实算 | 差在哪 |
|---|---|---|---|
| 橡树叶 → 木棍 | 0.05 | 0.03 | 手工值过时 |
| 女巫 → 红石 | 0.125 | 6.0 | 0.125 是旧版「额外掉落 0-2 个」的概率；26.3 是每只固定掉 4–8 个 |
| 女巫 → 萤石粉 | 0.125 | 0.2857 | 实际是「7 份权重里占 1 份、每池掷 2 次」 |
| 僵尸 → 铁锭 | 0.025 | 0.0083 | 0.025 是整池概率；池里铁锭/胡萝卜/土豆等权，铁锭只占 1/3 |

也就是说：这些数本来就在数据里，抄一遍只会抄错，而且会随版本过期。

## 决定

所有直接来源用同一个口径：**触发一次的期望产出件数**（`per_trigger_expected`）。

| 来源类别 | 触发方式 | 主键 `subject` |
|---|---|---|
| `block_drop` | `block_break` 破坏一次 | 方块 ID |
| `mob_drop` | `kill` 击杀一次 | 实体 ID |
| `loot_table` | `chest_open` 开一次 | 战利品表 ID（结构集合另有一行） |
| `shear` | `shear` 剪一次 | 实体 ID |
| `suspicious_block` | `brush` 刷一次 | 表名 |

统计层落成 `loot_expectation` 行，`trigger` 是必需字段；索引行新增
`yield_per_trigger` / `yield_condition` / `yield_source`，`probabilities.toml`
降为无人命中的兼容层（实测命中数 0）。

工具条件是**两行**，查询时取对目标物品更有利的那一行：橡树叶带剪刀只掉树叶，
徒手才掉木棍，模型不该替玩家选工具。

## 顺带修掉的三处解析缺口

1. **内联嵌套表**：`equipment/*` 把表直接写在 `value` 里（对象，不是表 ID）。旧实现
   当「未处理类型」丢掉，三张试炼厅装备表产出恒为 0。
2. **`unenchanted_chance` + `enchanted_chance`**：26.x 写法的附魔加成条件。旧实现只认
   `chances` 数组，整池被判为 0，僵尸的铁锭因此消失。
3. **`enchanted_chance` 的 `linear` 分布**（`base` / `per_level_above_first`）：
   取等级 0 的值。

## 后果

- `data/knowledge/probabilities.toml` 不再被命中。保留文件是因为「手工覆盖」仍是合法需求
  （数据里确实没有的量），但命中数应当长期为 0，非 0 就说明有一类来源没接上数据。
- 覆盖度：3128 条来源里 2542 条有推导值，586 条没有。**这 586 条就是缺口清单**，
  其中绝大多数是 `trade` 来源（交易条款尚未进统计层）。
- 已知缺口：掉落判定里有 `minecraft:match_block` 条件，26.3 数据包里 **295 处、191 张表，
  每一处都带 `state`**（`age=7`、`half=lower`、`part=head`、`type=double`、`candles=2|3|4`）。
  本侧目前把未知条件当不成立，于是产生两个具体错误：
  - `blocks/wheat` 是 `alternatives`：成熟分支（`age=7`）算 0，未成熟分支（种子）成了 1，
    结果「破坏小麦 = 只掉种子」。
  - `blocks/oak_slab` 把条件写在 `set_count` 函数上（双层才掉 2 个），而函数级条件
    根本没被检查，于是常量按 2 个计且不报 unsupported。

  修法：这些谓词绝大多数不是「世界分布」，而是「什么时候动手」——
  **游戏世界会变**（作物会长、蜂巢会满），所以允许等到状态合适再破坏时 `P=1`，
  代价转为一个**时间**量（`growth_wait_seconds`，归标定项），而不是一局静态分布。
  剩余不用等的谓词（`type=double`）是机制事实，直接取 0；
  只有「一次性且不可重试」的破坏才可能需要测量，目前没有作物型来源属于这类。
  因此不向上游提状态分布需求，见[上游数据需求](../contracts/upstream-requirements.md) 第 2 条（已撤销）。
