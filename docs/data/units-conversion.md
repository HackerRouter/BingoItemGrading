# 折算口径

节名与 [`units.md`](units.md) 同一套定义。

## 数量缩放

代价是在「拿 1 个」的前提下算的，但很多场景要多个。`--count N` 把三条来源按各自的规律放大：

| 来源 | 缩放规律 | 原因 |
|---|---|---|
| 挖矿 | **次线性** | 竖井（到达该层）记成带名字的固定成本（`reach:<维度>:<纵段>`），整个方案只收一次；矿道随数量线性 |
| 熔炼 | 线性 | 每个都要单独炼，燃料也按个数算 |
| 开箱 | **线性** | 每趟地点的投入（旅行 + 翻箱）与产出严格成比例，没有可摊薄的固定成本 |

实现上竖井不是摊进单价，而是 `Action.overhead` → 曲线段的 `fixed`，同名固定成本跨动作、跨层传递时只收一次（与「同一趟村庄」同一条去重规则）。实测：金锭主路线是开箱，代价严格 ×N；红石主路线是村庄牧师交易，`count` 放大时固定成本被摊薄。

这条规则让「批量拿」与「顺手拿一个」的分数差异自然浮现：数量越大，挖矿越占优；开箱不会因为量大而变便宜。

## 村民交易折算

村民交易把「A 物品 → B 物品」变成一条边：成本 = A 的成本 + 交易时间，产出 = B 的数量。

交易有时间成本但很小（每次 2 秒，约 0.29 TU），真正的成本在其换入物。要注意 `max_uses`：

| 量 | 值 |
|---|---|
| 每次交易 | 2 秒 |
| 牧师 `1 绿宝石 → 2 红石` | `max_uses = 12` |

`max_uses` 是**每名村民每次刷新**的成交上限，是硬约束。超出后要么等刷新（约两个游戏日），要么找下一个村民/下一处村庄——后者等价于「重复付旅行成本」。

一类常见结构是「翻箱顺带拿 A，A 换目标 B」。此时 A 的边际成本为零（同一趟已经付过），但产出受限于 A 在箱子里的期望量与 `max_uses`。红石的牧师路线就是这种，见 [ADR 0023](adr/0023-redstone-cleric-trade-route.md)。

`max_uses` 是**每名村民**的上限，不是每处村庄的。村庄里摆酿造台可以反复让无业村民转职，所以村庄级的容量 = 村民数 × `max_uses`。见 [ADR 0024](adr/0024-village-emerald-sources.md)。

## 非矿石方块的两种采集模型

同样是「挖方块拿材料」，代价算法取决于方块怎么分布：

| 模型 | 适用 | 公式 |
|---|---|---|
| `mining`（挖矿道） | 埋在岩层里的矿石 | 撞到一块要挖 `1/ρ` 个方块 |
| `surface_block_cost`（露头） | 粘土、沙子这类看得见的 | 找到首片（100 格）+ 带内走 + 挖掉 |

区别很大：粘土用矿道模型算出 28 TU/绿宝石，用露头模型是 1.06 TU，差 27 倍。粘土在河床成片躺着，玩家看得见，不需要「挖穿废石去碰」。

**露头模型只累加「地表区段」的量**：逐段判断「该段上方那一段是否敞开」（`fill_dry < 0.5`），只把敞开的段计入密度。全高密度里大半埋在地下，拿它当「走过去就能捡」会把走动距离低估几十倍：

| 方块 | 全高/区块 | 地表段合计 | 占比 |
|---|---|---|---|
| `bamboo` | 8.80 | 8.80 | 100% |
| `sand` | 85.62 | 68.27 | 79.7% |
| `gravel` | 513.60 | 82.39 | 16.0% |
| `clay` | 97.41 | 2.63 | **2.7%** |

注意不是「从最低的敞开段往上全部相加」而是**逐段判断**：中间可能夹着实心段（如 y48 敞开、y32 实心、y16 又是洞穴），简单从下往上加会把洞穴里的量也当地表量。没有任何敞开段时，露头模型直接缺席（返回 `None`），不能拿地下密度顶上。

**结构方块**是第三种情况：只在特定结构里生成的方块（干草块只在村庄马厩/动物栏）。它的分布不是「全图平均」，而是「每处结构有多少」：

```
每处结构的方块数 = 全图该方块总量 ÷ 结构数量
                 = block_density.total_blocks ÷ (chunks / spacing²)
```

干草块按全图平均算会得到 0.037 块/区块（要挖 960 区块才凑够一块），按结构算则是 42.9 块/村，差 1160 倍。

**结构本身的到达成本分两种**，不能混用：

| 情形 | 用什么 | 例子 |
|---|---|---|
| 看得见、位置可推 | `structure_nearest_distance`（期望最近距离）+ 竖井 | 村庄（地表跑图就能遇到） |
| 看不见、不在图上 | `structure_search_cost`（满图搜索） | 地牢（只能顺洞穴碰运气） |

搜索成本的模型：**体积占比**，不需要「通道截面」这种对大厅失效的换算。

```
玩家前进 1 格扫过 2 格³（1 宽 × 2 高）
命中概率 = 扫过体积 × (结构总体积 ÷ 地下总体积)
期望推进格数 = 地下总体积 ÷ (2 × 结构处数 × 每处占地体积)
```

实测（`26.3` 采样）：地下体积 1.09e9 格³ ÷ (2 × 7377 处 × 729 格³/处) = 期望挖 **101 格**，挖掘 11.6 + 走动 2.0 = **13.6 TU**。而「最近一处」只有 24 格——用后者等于假设玩家已经知道地牢在哪。

每处地牢的占地 = 9×9×9 = 729 格³（方形房间，版本事实）。

三个容易错的地方：

- **不要用「空隙体积 ÷ 通道截面」**。大厅体积大、穿过去只要几十格，除法会把一个大厅算成几百格通道。第一版就是这么做，配合另一个错误（下条）算出 9418 格。
- **空隙本身用 `1 - fill`（含水）**，不是 `1 - fill_dry`。地下水不是可通行空间，扣水会把水当成洞穴（y48~63 段 145 → 1603 格³，虚增 320%）。
- **地牢处数含深浅两种**（`monster_room` 与 `monster_room_deep`），但分子只算了 y≥0 的地下体积——下游只要浅层地牢。两个口径对不上，结果偏乐观；已作为 C15 报给采集侧。




## 挖掘折算

矿石、深层岩石这类「要动手挖」的来源，代价由 `src/bingo_grading/mining.py` 从密度统计换算，公式与常数都在 `units.py` 里。

**基本量**：一个区块地表占 `CHUNK_FOOTPRINT = 256` 个方块²。某纵段每区块有 `n` 块目标矿、段高 `h`，则该段的目标矿体积密度为

```
ρ = n / (256 × h)        单位：块矿 / 块岩石
```

密度越低表示要挖掉越多废石才能撞见一块，挖穿一块所需的废石数为 `1/ρ`。

**破坏耗时**（徒手、不含工具附魔，单位：秒/块）由 `hardness` 现算，不手抄，公式见本节末尾。

y < 0 默认围岩为 `deepslate`，否则 `stone`；下界整块是 `netherrack`。可用 `--break-block` 强行指定。

**各维度的竖井起点**（`SURFACE_Y_BY_DIMENSION`）：

| 维度 | 高度 | 理由 |
|---|---|---|
| 主世界 | 70 | 恶地陶瓦层厚，差 10 格以内，不单独建模 |
| 下界 | 50 | 玩家从传送门进来通常在 y 40–70 的岩层中；y 32 以下是熔岩海 |
| 末地 | 64 | 主岛平台 |

下界没有深板岩，整块都是下界岩（0.10 s/块，比石头软 4 倍）。这个差异是下界挖矿路线的核心优势，不能按主世界算——早期实现忽略它时，下界金矿被高估了约 4 倍（60 TU vs 实际 15 TU）。

**两条代价**相加得到该纵段的代价：

```
矿道  tunnel = (目标数量 / ρ) × 破坏秒数 / SECONDS_PER_TU
竖井  shaft  = 纵段深度 × 截面(1×2) × 破坏秒数 / SECONDS_PER_TU
```

**破坏秒数不再手写**：`hardness × (1.5 正确工具 / 5.0 错误) / 材质速度`，数据来自上游
`facts/mining.jsonl` 与 `mining_tool_materials.jsonl`（见 `mining_facts.py`）。矿道/竖井按
**铁质工具**计，其余按石质（项目特化口径在 `gamedata.py`）。

`SECONDS_PER_TU = 1.0`（秒数即 TU），`gamedata.DEFAULT_SWATH = 2`（1 宽 × 2 高）。竖井从地表 `SURFACE_Y = 70` 打到该段顶部。

竖井是**到达成本**，不是每件成本：它进动作的 `overhead`，在曲线上变成带名字的固定项（`reach:<维度>:<纵段>`），所以拿 N 件只挖一次井。多个纵段时取总代价最小的那一段作为该群系的代表，因此结果天然反映「就近挖浅的」而非「挖最富的」。

**两个简化及其后果**：

- 竖井按实心掘进计，不含洞穴、峡谷、废弃矿井等现成空腔。有那些结构时实际代价更低，所以竖井项是上界（见 [ADR 0014](adr/0014-air-exposure-cave-conflation.md) 关于现有数据无法区分地表露头与洞穴壁的说明）。
- 矿道按「挖穿 `1/ρ` 个方块必遇一块矿」计，不建模矿脉成簇。簇状分布下实际略有偏差，但同一群系内对比时偏差方向一致，不影响群系间的相对排序。

矿石掉落多个时（红石 4–5、青金石 4–9），用 `entries_per_block` 把「要挖几块矿」除以平均掉落数，只影响矿道项，不影响竖井项。

**工具是普通物品**：挖矿动作挂一个 `once` 前置（最弱合格工具由 RA 的 `harvest.jsonl` 给出），工具成本由配方链递归算出（配方里的 `#tag` 原料已展开）。例：铁镐 = 3 铁锭 + 2 木棍 + 熔炼 + 采集，在方案里只收一次。

**多候选槽全部展开，不在这里挑一个**。`#minecraft:logs` 这类槽位有几十个成员，每个可行候选 × 每条配方的组合都建一个动作，最便宜的那个用 `tool:craft:<物品>`，其余按代价升序编号 `~2`、`~3`……于是「用 `oak_wood` 要多贵」这件事由引擎自己算出来（0.346 vs 直接砍 `oak_log` 的 0.259 TU），能在曲线里重放最优与次优，而不是在构建阶段被切断、永远看不见。

为此 `estimate_cost` 只做两件事：筛掉无来源候选（`inf`）、给组合排序编号。它**不再替调用方拍板**。环配方（铁粒 ← 烧铁工具 ← 铁锭 ← 铁粒）在展开时按「同一路径不能自给」判不可行，否则会灌进一堆「烧铁镐换铁粒」的荒谬动作。

## 采集模型

同一个方块常常三种取法都成立，所以**三条来源都摆上**，由引擎按需求量取舍：

| 模型 | 含义 | 固定成本 |
|---|---|---|
| `mine_surface`（地表/水下） | 走到资源带，挖掉 `n` 个 | 找到首片（100 格） |
| `mine_cave`（洞穴） | 走到洞口、沿洞穴下潜、走过去挖 | 走到洞口 + 下潜距离（洞穴通道现成，不挖竖井） |
| `mine_vein`（矿道） | 挖竖井下去、开矿道碰运气 | 竖井（同维度同深度带只付一次） |

粘土就是典型：地表（河床、水下）每区块能捡到几块但走过去就行，地下量大却要挖矿道，洞穴里则介于两者之间。二选一会把便宜的那半边丢掉。

三者各有更优区间，所以**剪枝不能只看单价**：洞穴单价略低但到达更贵，小需求量下地表仍然更优（`_dominates` 会逐项比较 `overhead`，否则会把正确的最优剪掉）。

**可得密度用实测暴露算，不用段估算**：`block_exposure` 给出该方块贴天空 / 水 / 洞穴空气 / 埋着的比例（上游 6 面邻接判定），乘上全高密度就是「走过去能捡到的量」。`sky + water` 算地表档，`cave` 算洞穴档。

| 方块 | 天空 | 水 | 洞穴 | 埋着 | 地表档 | 洞穴档 |
|---|---|---|---|---|---|---|
| `bamboo` | 96.4% | 0% | 0.1% | 3.5% | 96.4% | 0.1% |
| `sugar_cane` | 99.9% | 0% | 0.7% | 0.05% | 99.9% | 0.7% |
| `sand` | 9.3% | 42.2% | 0.2% | 49.3% | 51.5% | 0.2% |
| `oak_log` | 44.6% | 0.6% | 8.0% | 46.6% | 45.2% | 8.0% |
| `clay` | 0.009% | 4.8% | 6.3% | 88.7% | 4.8% | 6.3% |
| `gravel` | 0.2% | 13.4% | 2.5% | 83.1% | 13.7% | 2.5% |

**没有暴露数据的方块不给地表/洞穴来源**：段填充率只能说明「这段整体敞开不敞开」，说明不了「方块自己露不露」。`iron_ore` 在 y48~63 段有 1.7 块/区块、上方段是空气，按段级数据会算出 1.07 TU/个，实际要挖 14 TU。宁可保守（只走矿道），不造假来源。

**样本量判据**：算代价前先看这条密度统计数到了多少块目标方块（`total_blocks`）。低于 `MIN_DENSITY_BLOCKS = 200` 时密度估不稳，代价标为仅供参考。判据用方块数而不是区块数——理由见 [ADR 0019](adr/0019-density-sample-size-in-blocks.md)。上游的区块级 `reliable` 只作为信息字段随输出带出，不参与过滤。

## 熔炼折算

金锭这类需要熔炼的物品，代价 = 冶炼时间 + 燃料折算：

| 量 | 值 | 说明 |
|---|---|---|
| `SMELT_SECONDS` | 10.0 秒/个 | 熔炉 200 tick；高炉是 100 tick，但要先做高炉（铁锭 + 平滑石），单个不划算 |
| `SMELTS_PER_FUEL` | 8 | 一份煤炭 = 1600 tick |

燃料按「挖煤」计：`燃料份数 = 物品数 / 8`，乘上煤的最优挖掘代价。煤的密度极高（60+ 块/区块），这项很小但并非为零。缺煤数据时退化为只算冶炼时间，并在 `assumptions` 里标注。

燃料不是「顺带就有的」——它真的要从别处挖来。但冶炼是串行的（一个熔炉一次只炼一个），所以时间不能通过并联缩短。
